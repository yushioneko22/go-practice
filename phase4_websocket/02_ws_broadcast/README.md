# 02 WebSocket Broadcast (複数人への同時配信と Hub 構成)

このトピックでは、**「複数のクライアントを管理し、誰かの発言を全員に一斉送信（ブロードキャスト）する」**ためのデザインパターンを学びます。

---

## 1. なぜ必要か
一対一の通信（オウム返し）だけでは、チャットアプリやマルチプレイヤーゲームは作れません。
サーバー側で「今誰が繋がっているか」のリストを保持し、一箇所に送られたメッセージを全員に配る **Hub（中継役）** の仕組みが必要になります。ここでの設計力が、大規模なリアルタイムシステムの基盤となります。

## 2. 比喩：Hub は「司会者」や「中継放送局」
- **Client**: 観客（話したり聞いたりする人）。
- **Hub**: 司会者。マイク（メッセージ）を受け取り、それを会場のスピーカー（全員への送信処理）から流す役割。誰が客席に座っているかも把握している。

## 3. コード解説

### 01. クライアント管理用の構造体 (10-15行目)
```go
type Hub struct {
    clients    map[*Client]bool
    broadcast  chan []byte
    register   chan *Client
    unregister chan *Client
}
```
`map` で接続中のクライアントを管理し、各種 `chan`（チャネル）を使って「新しい人が来た」「誰かが帰った」「全員に送れ」といった指示を交通整理します。

### 02. メインループ (20-35行目) ★ここが一番重要
```go
func (h *Hub) Run() {
    for {
        select {
        case client := <-h.register:
            h.clients[client] = true
        case message := <-h.broadcast:
            for client := range h.clients {
                client.send <- message
            }
        }
    }
}
```
`select` 文を使うことで、複数のチャネルを同時に待ち受け、データの競合（書き込みの衝突）を防ぎながら安全に処理します。

---

## 4. 重要なTips
> [!TIP]
> 1. **スレッドセーフ**: Goのマップは複数の場所から同時に書き込むと壊れますが、今回のように「一つの `Run` ゴルーチン（Hub）」の中だけで操作するように設計すれば安全です。
> 2. **バッファ付きチャネル**: `chan []byte` を作る際、少し余裕（容量）を持たせておくと、一瞬の大量送信でも処理が詰まりにくくなります。
> 3. **お掃除の重要性**: クライアントが切断されたら必ず `unregister` を通じてリストから消さないと、サーバーのメモリがどんどん食いつぶされてしまいます。

## 5. まとめ
「Hubを通したブロードキャスト」は、リアルタイムシステムの王道パターンです。これが理解できれば、世界中の人と繋がるアプリが作れます。

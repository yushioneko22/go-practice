# 01 URL短縮サービス

このトピックでは、**システムデザイン面接の定番「URL短縮サービス」の設計とGoによるプロトタイプ実装**を学びます。

## なぜ必要か

URL短縮（bit.ly, TinyURL）はシステムデザイン面接の最頻出問題です。「簡単そうに見えて、スケーリングの考慮点が多い」という特徴があり、候補者の設計力を幅広く試せます。

## たとえ話

URL短縮は「本の索引ページ」です。
- 長いURL = 本文中の詳しい説明（読むのに時間がかかる）
- 短縮URL = 索引の「P.42参照」（一瞬でアクセスできる）
- 索引の管理 = 短縮コードとURLの対応をどうやって保存・検索するか

---

## 面接での設計ポイント

### 1. 要件定義
- 短縮URLの生成（Write）
- 短縮URLからリダイレクト（Read）
- 読み書きの比率は？（通常 100:1 で読みが圧倒的に多い）

### 2. データモデル
| カラム | 型 | 説明 |
|:---|:---|:---|
| short_code | VARCHAR(7) | Base62エンコードされた短縮コード |
| original_url | TEXT | 元のURL |
| created_at | TIMESTAMP | 作成日時 |

### 3. Base62エンコーディング
[0-9a-zA-Z] の62文字で表現。7文字で 62^7 ≒ 3.5兆のURLをサポート。

### 4. スケーリング
- キャッシュ: Redis/Memcachedで頻繁にアクセスされるURLをキャッシュ
- 分散: 複数サーバー間でのID衝突をどう防ぐか（DB auto-increment、Snowflake ID等）

---

## example/main.go の解説

### 1. Base62エンコーディング (12-30行目) ★ここが一番重要
IDをBase62文字列に変換する関数。これが短縮コードの生成ロジック。

### 2. インメモリストア + HTTPサーバー (32-70行目)
簡易的なURL短縮サーバー。POST で短縮URL生成、GET でリダイレクト。

---

## 重要なTips

> [!TIP]
> 1. **ハッシュ衝突**: MD5/SHA256のハッシュを使う場合、衝突時のリトライ戦略を説明しましょう。
> 2. **カスタムURL**: ユーザーが短縮コードを指定できる機能は面接で追加質問されやすい。
> 3. **分析機能**: クリック数、リファラー、地域情報の収集など、ビジネス要件も考慮すると好印象。

cd example

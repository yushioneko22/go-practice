# 02 Rate Limiter（レート制限）

このトピックでは、**APIの過負荷を防ぐ「Rate Limiter」の設計とGoでの実装**を学びます。

## なぜ必要か

DDoS攻撃やバグによる大量リクエストからシステムを守るため、Rate Limiterは本番サービスに必須です。面接では「Token Bucket」「Sliding Window」などのアルゴリズムの違いを説明できることが求められます。

## たとえ話

Rate Limiterは「遊園地の入場制限」です。
- 1時間あたり最大100人まで入場可能
- 101人目は「お待ちください」と言われる
- Token Bucket: 一定時間ごとにトークン（入場券）が補充される
- Sliding Window: 過去1時間のリアルタイムなカウント

---

## アルゴリズム比較

| 方式 | 仕組み | メリット | デメリット |
|:---|:---|:---|:---|
| Token Bucket | トークンを一定速度で補充、リクエストごとに消費 | バースト対応可能、実装が簡単 | メモリ効率はやや悪い |
| Fixed Window | 固定時間窓ごとにカウント | 実装が最も簡単 | 窓の境界でバースト可能 |
| Sliding Window | 過去N秒間のリクエスト数をカウント | 最も正確 | 実装が複雑、メモリ使用量多 |

## 重要なTips

> [!TIP]
> 1. **分散環境での課題**: 複数サーバーで動作する場合、Redisなどの共有ストアでカウントを管理する必要があります。
> 2. **HTTPヘッダー**: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `Retry-After` を返すのがベストプラクティス。
> 3. **グレースフル・デグラデーション**: Rate Limiterの障害時は「全拒否」ではなく「全許可」にフォールバックすべきです。
